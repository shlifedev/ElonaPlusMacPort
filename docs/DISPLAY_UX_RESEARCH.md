# 화면 해상도·글꼴·시스템 팝업 조사

**후속 수정.** 아래는 수정 전 조사 기록이다. `2e4f93a`에서 `chgdisp`를 SDL 창의 데스크톱 전체 화면과 연결했다. 현재 Mac Release는 사용자 설정 복사본의 1280×768 전체 화면으로 시작한다. [수정 후 실행 결과](ASTRA_62_REVIEW.md)

조사일: 2026-11-18. 최신 사용자 요청에 따라 **조사만 수행**했다. 이 문서를 위해 게임 코드, 사용자 설정, 실행 중인 창을 변경하지 않았다. 아래 개선안은 구현 완료 사항이 아니다. 이전에 승인받아 구현·검증한 조작 안내 창 닫기 개선은 별도로 구분한다.

## 확인된 결론

- 원본 게임은 메뉴에서 최대 **1280×768**을 선택할 수 있다. 창을 마우스로 크게 만드는 것과 게임이 그리는 논리 해상도를 바꾸는 것은 다르다. 현재 네이티브 창 크기 변경은 기존 화면을 확대하는 방식이다.
- Retina 대응 창은 이미 사용한다. 다만 글자와 타일을 낮은 논리 해상도의 CPU 화면에 먼저 그린 뒤 전체를 확대한다. 따라서 Retina 창이라는 사실만으로 글자가 고해상도로 다시 그려지지는 않는다.
- 확대 텍스처에는 nearest를 명시한다. 과거 Mac 2배 캡처와 원본 화면의 비교도 픽셀 불일치 0이었다. 현재 사용자가 느낀 흐릿함을 단순히 bilinear 필터 탓이라고 단정할 근거는 없다. 작은 크기에서 안티앨리어싱한 글자 자체를 확대하는 경로, 글꼴 대체 및 비정수 배율을 따로 확인해야 한다.
- 최신 사용자 실행 `play-q_h9nwc4`는 **전체 화면 설정 → 미구현 `chgdisp` 호출 → 명시적 종료**다. 이 실행에는 팝업도 창 닫기 이벤트도 없었다. 이전 조작 안내 창 닫기 문제와 다른 원인이다.
- `msg_box.=1`은 이름 입력창의 표시 방식을 고르는 설정이다. 라이선스 등 모든 OS 메시지박스를 게임 내부 UI로 바꾸는 전역 설정은 아니다.

## 최신 종료: 전체 화면 전환이 미구현

읽기 전용으로 확인한 `work/player/2.335/sessions/play-q_h9nwc4/report.json`:

| 항목 | 관측값 |
|---|---|
| 빌드 | arm64, `Nov 18 2026 08:32:57`, 진단 형식 2 |
| 종료 | `exit_code=3`, `exit_reason=unsupported`, frame 22 |
| 최초 미지원 | `command: chgdisp line=-1 file=vernis` |
| 팝업 / 창 닫기 / 관찰 HSP 오류 | 각각 0 / 0 / 0 |

사용자 `config.txt`는 `fullscreen.=1`, `windowW.=1280`, `windowH.=768`이다. 원본 기본 설정은 전체 화면 0, 800×600이다. 보정 참조 소스 `work/decompiled/2.335-reference/start.hsp:23722`는 전체 화면일 때 `chgdisp 1, windoww, windowh`를 먼저 실행하고, 다음에 `bgscr`를 만든다. 창 모드 분기는 `screen`을 호출한다. 현재 호스트는 `chgdisp` 이름을 인식하지만 구현 분기가 없어 미지원 종료를 낸다. 이것으로 이번 실행의 종료 경로를 설명할 수 있으며, 한국어 문자열이 원인이라는 근거는 없다. 보고서의 `file=vernis`는 런타임 진단 문자열이고, 실제 베르니스 맵에 도착했다는 뜻으로 해석하지 않는다.

`src/platform/window_sdl.cpp`에는 `SDL_SetWindowFullscreen`을 호출하는 `set_fullscreen`이 있으나, 이것을 부르는 게임 명령 연결은 없다. 특히 원본 `chgdisp` 호출 시점에는 대상 창을 아직 만들지 않았으므로 API 한 줄 연결만으로 계약이 완성되지 않는다.

원본 동작의 참고 근거는 고정 OpenHSP `3dbb8729dad53ee876fc681696c8fe542698860b`의 `src/hsp3/win32gui/hsp3gr_wingui.cpp:74` 및 `:493`이다. mode 1은 요청한 화면 크기의 디스플레이 모드를 열거해 색 깊이를 선택하고 `ChangeDisplaySettings`로 실제 모니터 모드를 바꾼다. mode 0은 이전 모드를 복원한다. 일치하는 모드가 없으면 1을 반환한다. 실패 분기에서 `ctx->stat=2`를 쓴 뒤 호출자가 반환값으로 덮어쓰는 코드도 있으므로, 문서상 반환값만 보고 이식하면 안 된다. **동봉 원본 런타임의 전체 화면 실패 반환값을 x86에서 실측한 것은 아니다.**

향후 선택지는 다음과 같다. 이번 조사에서는 어느 것도 적용하지 않았다.

| 선택지 | 장점 | 구현·검증에서 필요한 것 |
|---|---|---|
| 모니터 모드를 바꾸지 않는 전체 화면 창 | OS 화면 전환 부담이 작고 Retina 출력과 조합 가능 | `chgdisp` 요청을 창 생성까지 보존, 논리 해상도/여백/입력 좌표, 전환 실패·복원·다중 모니터 검증. 원본과의 정책 차이를 명시 |
| 원본처럼 실제 디스플레이 모드 변경 | 원본 Win32의 의미에 가까움 | 지원 모드 목록, 미지원 크기 반환값, 포커스 상실·종료·실패 시 복원, Mac/Windows 차이를 실제 검사 |
| 런처의 명시적 창 모드 복구 선택 | 이미 전체 화면으로 저장된 프로필을 복구 가능 | 사용자에게 일시적 선택을 보여주고 적용 범위 설명. 사용자 설정을 몰래 0으로 덮어쓰거나 `chgdisp`를 더미 성공 처리하지 않음 |

## 해상도의 세 층

| 층 | 현재 동작 | 크기를 키웠을 때 |
|---|---|---|
| 게임 논리 화면 / HSP DIB | 원본 게임의 `screen`, `buffer`, `windowW/H`가 결정 | 원본이 지원하는 범위에서는 더 넓은 게임 영역을 그릴 수 있음. 글꼴·타일 원본의 세부 묘사가 늘어나는 것은 아님 |
| OS 창 크기 | SDL 창, 사용자가 크기 조절 가능 | 현재는 고정 논리 화면을 비율 유지 확대·축소하고 남은 공간은 여백으로 처리 |
| 실제 디스플레이 픽셀 | `SDL_WINDOW_HIGH_PIXEL_DENSITY` 사용 | Mac Retina에서는 같은 창 좌표에 더 많은 물리 픽셀을 쓸 수 있으나, 현재는 같은 CPU 이미지의 확대 결과 |

SDL 공식 문서는 창 좌표 크기와 실제 픽셀 크기를 구분하며, Mac과 Windows의 DPI 좌표 규칙도 다르다고 설명한다. 실제 출력 크기는 `SDL_GetWindowSizeInPixels` 등으로 읽어야 한다. [SDL High DPI 안내](https://wiki.libsdl.org/SDL3/README-highdpi)

로컬 구현 근거는 `src/platform/window_sdl.cpp:32–98`이다. 창은 high pixel density와 resizable 플래그로 만들고, `SDL_LOGICAL_PRESENTATION_LETTERBOX`에 논리 너비·높이를 고정한다. CPU BGR DIB를 같은 크기의 RGB24 텍스처로 복사한 후 확대한다. 텍스처는 `SDL_SCALEMODE_NEAREST`를 요청한다. SDL의 논리 프레젠테이션은 설정한 논리 크기를 실제 출력에 맞추어 확대하는 기능이다. [SDL 논리 프레젠테이션](https://wiki.libsdl.org/SDL3/SDL_SetRenderLogicalPresentation), [SDL 텍스처 배율 설정](https://wiki.libsdl.org/SDL3/SDL_SetTextureScaleMode)

`translate`에는 window resize/pixel-size/display-scale 이벤트를 받아 HSP 게임 버퍼를 다시 만드는 경로가 없다. 마우스 이벤트는 `SDL_ConvertEventToRenderCoordinates`, IME 입력 영역은 `SDL_RenderCoordinatesToWindow`로 변환한다. 따라서 창의 시각적 확대와 논리 좌표 입력을 맞추는 구조는 있으나, DPI/여백 조합별 실제 입력·IME 검증은 별도다.

기존 실행 증거:

- `run24/cwd/shots/s2285-name-window.bmp`: 1600×1200 창 출력. 게임 논리 화면은 800×600이다.
- `build/native-macos-arm64-legacy-cp932-debug/gui-fixtures-window/screens/text_wait-screen0.bmp`: 200×60. `text_wait-window.bmp`: 400×120.
- 같은 fixture 결과의 `window_capture.scale=2`, `mismatches=0`: 검사한 장면은 정확한 2배 픽셀 확대였다.
- 현재 사용자 설정의 1280×768은 최신 실행에서 화면 생성 전에 중단됐다. 그 설정으로 현재 화면 품질이 검증됐다고 표현하면 안 된다.

## 원본 게임이 허용하는 해상도

설정 메뉴 소스 `start.hsp:608295–608321`의 실제 선택 가능 목록:

| 선택 번호 | 논리 해상도 | 800×600 대비 화면 픽셀 수 |
|---|---|---|
| 0 | 800×600 | 1.00배 |
| 1 | 800×696 | 1.16배 |
| 2 | 1024×768 | 1.64배 |
| 3 | 1152×864 | 2.07배 |
| 4 | 1280×768 | 2.05배 |

배열에 1280×1024도 있지만 인덱스를 0–4로 제한하고 검색도 5개만 하므로 현재 메뉴에서 선택할 수 없다. 별도로 게임 화면 배치 계산 `start.hsp:205320`에는 `windowh>868`이면 868로 줄이는 코드가 있다. 설정 파일을 임의로 1920×1080 또는 4K로 바꾸는 것이 정상 지원 범위라고 말할 수 없다. 원본 설정 주석도 너비 최소 800, 높이 최소 600, 4의 배수를 요구한다. 너비의 임의 상한이나 모든 조합의 동작을 이번 조사에서 실측하지 않았다.

설정의 `fontSize.=14`, `tileSize.=48`은 원본 파일에서 “unavailable / please do not change” 구역에 있다. 이것을 UI 배율 옵션처럼 안내하면 안 된다. 실제 게임은 장면마다 `font` 크기를 지정한다.

## 글자가 흐릿해 보일 수 있는 경로

`src/graphics/text_renderer_ttf.cpp`에서 확인한 사실:

1. 원본 글자는 지정 논리 크기로 `TTF_RenderGlyph_Blended`를 호출해 안티앨리어싱한 뒤 24-bit CPU DIB에 합성한다. 기본 antialias는 true이고 폰트 힌팅은 normal이다.
2. CP932 호환 배치는 반각 `px/2`, 전각 `px` 셀을 사용한다. 실제 글꼴의 비례 폭을 그대로 쓰지 않는다. 현재 한국어 표시도 논리 화면에 그려진다.
3. 원본이 “MS Gothic”/“Courier New”를 요청해도 현재 렌더러는 후보 파일에서 선택한 글꼴을 쓴다. Mac 기본 일본어 폰트는 Hiragino 계열, 한국어 후보는 Apple SD Gothic Neo/AppleGothic이다. Windows는 MS Gothic, 한국어는 Malgun/Gulim 후보다. 원본 요청 이름이 그대로 표시 글꼴이라는 뜻은 아니다.
4. 초보자 조작 안내 창은 원본 `start.hsp:609519`에서 영어일 때 11, 일본어일 때 13의 작은 논리 글꼴 크기를 지정한다. Retina에서 2배 확대해도 11픽셀에서 이미 만들어진 글자 가장자리를 확대한다.

따라서 “Retina 픽셀이 부족하다”보다는 **작은 글자 래스터를 화면 전체와 함께 확대하는 방식**이 우선 확인할 대상이다. 비정수 크기로 창을 늘릴 때 nearest 픽셀 폭이 균일하지 않아 보일 가능성, 글꼴 대체·셀 폭에 따른 가독성 차이도 있다. 이는 구현에 근거한 원인 후보이며, 사용자가 흐릿하다고 느낀 정확한 창 크기·모니터 배율·부분 화면을 읽어 측정한 결론은 아니다. 이번 요청에서는 사용자 창을 조작하지 않았다.

## 시스템 팝업은 종류별로 구분해야 한다

| 사용자에게 보이는 창 | 원본/현재 구현 | 기존 설정의 범위 |
|---|---|---|
| 시작 시 이용 안내·라이선스 | 원본 HSP `dialog` → 현재 `SDL_ShowMessageBox`; OS 모양의 모달 창 | `title_dialog.`가 이 안내를 제어. `msg_box`와 별개. 안내 내용을 삭제하는 개선은 검토하지 않음 |
| 오류·확인 메시지 | 원본의 여러 `dialog` 호출 → SDL 모달 | OK/Yes/No 결과가 게임 분기에 쓰일 수 있어 임의 자동 승인 금지 |
| 캐릭터 생성 뒤 초보자 조작 안내 | 원본 `screen 20`, 800×190 별도 게임 창 | `operate.`가 생성 여부 제어. OS 메시지박스가 아님 |
| 이름 입력란 | 원본 `mesbox` 계열을 현재 호스트의 가상 Edit/표시 오버레이로 재현 | `msg_box=0`: 보이는 입력 컨트롤. `msg_box=1`: 게임이 그린 입력 표시와 편집 컨트롤 연결 |
| NPC 대화·선택지 | 게임 화면에 직접 그린 창 | 일반적으로 OS 메시지박스가 아님 |
| IME 후보·조합 UI | SDL 입력과 OS 입력기 | 게임 내부 표시만 바꿔 해결할 수 있는 항목과 OS 후보 창을 구분해야 함 |

`msg_box` 원본 주석은 “0=windows message box 1=original message box”이지만 실제 코드 `start.hsp:309006–309075`는 이름 입력 루틴이다. 두 분기 모두 `mesbox`를 사용하고, 1일 때 숨긴 입력 컨트롤/게임 자체 표시 및 `aplsel`, `aplobj`, `apledit`를 조합한다. 이 경로를 바꾸면 IME·입력 포커스·호환 명령까지 확인해야 한다. 라이선스는 `start.hsp:308479`의 `cfg_titledialog`에 별도로 묶여 있다.

현재 `src/platform/window_sdl.cpp:186`은 OK=1, Yes=6, No=7 버튼을 만들며 Return/Escape 기본 버튼도 정한다. `src/app/gui_host.cpp`의 `dialog` 명령이 이 결과를 VM `stat`에 돌려준다. 기존 별도 Mac 실제 모달 fixture에서 1/6/7/1 반환을 확인했고 닫기 이벤트·HSP 오류는 없었다. 증거는 `work/modal-investigation/summary.json` 및 [PLAY_EXIT_INVESTIGATION.md](PLAY_EXIT_INVESTIGATION.md)다. 파일/색상 선택 dialog 모드 및 일부 원본 `_fdialog`/`exec` 경로는 미지원이므로 일반 메시지박스 구현과 혼동하면 안 된다.

이전 조사에서 조작 안내 창(screen 20)을 닫으면 원본의 전역 onexit가 게임 전체를 끝내는 것을 실제 Mac 창으로 재현했다. **이미 승인받아 구현된** `--auxiliary-close-hide`는 그 창만 숨기고 메인 창의 종료 의미를 유지한다. 기본 직접 호스트는 참조 동작을 유지하고 플레이 런처가 옵션을 켠다. 안내문도 표시 단계에서만 이에 맞게 바꾼다. 실제 창 닫기 후 이동·인벤토리·저장·새 프로세스 로드를 확인했다. 이 기존 개선과 최신 `chgdisp` 종료를 구분한다.

해상도 면적 비율은 연산 시간 벤치마크가 아니라 비용을 검토할 때의 기초 수치다. 단순 GPU 표시 확대는 CPU 논리 버퍼를 키우는 것과 비용이 다르다. 현재 vsync는 0이며, 실제 프레임 시간·전력·오디오 연동 성능은 별도 측정이 필요하다.

검토 순서는 전체 화면 시작 실패 처리 → 논리/창/물리 픽셀 및 실제 글꼴 진단 수집 → 원본 지원 해상도와 정수 배율 비교 → 글자 전용 고밀도 표시 실험 → 메시지박스 UX 통합이 합리적이다. **새 사용자 승인이 필요한 구현 결정은 root가 요청 범위에 따라 판단하며, 이 조사에서는 설정이나 동작을 변경하지 않았다.**
